# 파이널 유도 멀티짐 운영 MVP

역할 기반 Next.js 운영툴 MVP입니다. 랜딩페이지가 아니라 체육관 운영자가 매일 쓰는 내부 운영 화면, 서버 API, 권한 스코프, 변경 기록 흐름을 먼저 검증하도록 만들었습니다.

## 실행

```bash
npm install
npm run dev
```

브라우저에서 [http://localhost:3000](http://localhost:3000)을 열면 `/app/dashboard`로 이동하고, 세션이 없으면 `/login`으로 안내됩니다.

## 운영 계정 로그인

로그인 화면의 기본 운영 계정은 이메일과 임시 비밀번호를 사용합니다. 데모 seed와 파일럿 CSV import 계정은 기본 임시 비밀번호 `FinalJudoPilot!2026`의 서버 전용 PBKDF2 해시를 받으며, API 응답과 클라이언트 bootstrap 스냅샷에서는 `passwordHash`를 제거합니다. seed와 로그인 검증은 하나의 공유 해시 계약을 사용하고, 과거 관리자 seed 해시는 런타임 로드 시 정확히 일치하는 기존 관리자 계정만 현재 해시로 올려 기존 데이터 초기화 없이 로그인할 수 있게 합니다.

- 총괄 어드민: `admin@finaljudo.kr`
- 대표: `owner@finaljudo.kr`
- 코치: `coach@finaljudo.kr`
- 학부모: `guardian@finaljudo.kr`
- 회원: `member@finaljudo.kr`

실제 파일럿 전에는 `/app/admin/users`에서 발급 사유를 남기고 기본 임시 비밀번호를 계정별 일회성 값으로 교체한 뒤, 배포 환경에 기본값이 남아 있지 않은지 확인합니다.

## 데모 역할

개발/테스트 환경에서는 로그인 화면 또는 `/select-role`에서 비밀번호 없이 다음 역할 중 하나를 선택합니다. production에서는 `/select-role`이 이메일 로그인 안내만 표시하고 데모 역할 로그인이 기본 차단되며, 파일럿 검증용으로만 `FINAL_JUDO_ENABLE_DEMO_LOGIN=1`을 명시해 열 수 있습니다.

- 대표: 지점 대시보드, 내 지점, 운영 리포트, 회원, 수업, 결제, 공지
- 코치: 담당 수업, 출석 체크, 담당 회원, 공지
- 학부모: 자녀 수업, 출석, 결제, 공지
- 회원: 본인 수업, 출석, 결제, 공지
- 총괄 어드민: 전체 지점, 사용자, 권한, 변경 기록, 운영 설정

## 서버 API

MVP는 Next.js Route Handler를 사용합니다. 기본 개발 모드는 `PILOT_DB_FILE` 또는 `FINAL_JUDO_DATA_DIR` 기반 JSON 파일 저장소이고, 파일럿 운영 DB는 `FINAL_JUDO_DB_DRIVER=postgres`와 PostgreSQL JSONB 런타임 저장소로 전환할 수 있습니다.

- 로그인/로그아웃: `/api/v1/auth/login`, `/api/v1/auth/logout`
- 초대/재설정: `/api/v1/admin/users/invitations`, `/api/v1/auth/invitations/:token/accept`, `/api/v1/auth/password-reset`, `/api/v1/admin/users/:userId/password`
  - 총괄 어드민은 전체 역할 초대, 대표는 자기 지점 범위의 코치/학부모/회원 초대
  - 로그인 화면의 회원가입은 `/signup`에서 초대 링크 또는 코드를 입력받아 기존 `/invite/:token` 수락 화면으로 연결
  - 초대 수락은 12자 이상 초기 비밀번호 설정이 필요하며 기본 임시 비밀번호 `FinalJudoPilot!2026`과 이미 사용된 초대 링크는 차단
  - 총괄 어드민은 사용자별 임시 비밀번호를 발급하고 원문 비밀번호 없이 `auth.password_reset.complete` 변경 기록을 남김
- 세션 스냅샷: `/api/v1/me/bootstrap`
- 지점 관리: `/api/v1/admin/branches`, `/api/v1/admin/branches/:branchId`, `/api/v1/admin/branches/:branchId/owner`
- 출석 저장: `/api/v1/class-sessions/:sessionId/attendance`
- 출석 저장과 출석 사유 기록은 세션과 역할/지점/담당 수업 권한 확인을 요청 본문 검증보다 먼저 수행합니다.
- 회원 관리: `/api/v1/branches/:branchId/members`, `/api/v1/members/:memberId`
  - 대표/총괄은 상태/띠/레벨/긴급 연락처/주의사항 수정, 회원/학부모는 본인/자녀 긴급 연락처 수정
- 보호자 연결: `/api/v1/members/:memberId/guardians`
- 회원 등록/수정, 보호자 연결, 상담/주의 메모 작성은 세션과 역할/지점/회원 접근 권한 확인을 요청 본문 검증보다 먼저 수행합니다.
- 수업 관리: `/api/v1/branches/:branchId/classes`, `/api/v1/classes/:classId`
- 수업 생성과 수정은 세션과 대표/총괄 권한, 지점 접근 권한을 요청 본문 검증보다 먼저 수행합니다.
- 결제 관리: `/api/v1/branches/:branchId/payments`
- 온라인 결제 요청/webhook/정기결제 약정: `/api/v1/payments/:paymentId/online-checkout`, `/api/v1/payments/webhook`, `/api/v1/payments/:paymentId/recurring-agreement`
- 환불/취소 처리: `/api/v1/payments/:paymentId/refund`
- 수기 결제 등록, 환불/취소, 정기결제 약정 생성/해지는 세션과 역할/지점 권한 확인을 요청 본문 검증보다 먼저 수행합니다. 수기 등록은 부분 환불 상태를 직접 만들 수 없고, 부분 환불은 실제 환불 금액이 기록되는 환불 API에서만 생성됩니다. 취소 또는 환불 완료 상태로 바로 등록할 때는 사유가 필수이며, 정규화한 사유를 최초 상태 이력, `payment.create` 감사 스냅샷, 중복 방지 확인값에 함께 보관합니다.
- CSV 내보내기: `/api/v1/exports/payments`, `/api/v1/exports/operations`
- 권한 관리: `/api/v1/admin/users/:userId/roles`
- 변경 기록: `/api/v1/admin/audit-logs?reason=...`
- 파일럿 준비 상태: `/api/v1/admin/pilot-readiness`
- 파일럿 이슈 로그: `/api/v1/admin/pilot-incidents`, `/api/v1/admin/pilot-incidents/:incidentId`
- 파일럿 운영 로그: `/api/v1/admin/pilot-operations`
- 파일럿 준비 상태, 운영 이슈, 운영 로그 저장은 총괄 권한 확인을 요청 본문 검증보다 먼저 수행합니다.
- 요청 기능 삭제: `/api/v1/requests`, `/api/v1/requests/:requestId/approve`, `/api/v1/requests/:requestId/reject`는 제공하지 않아 직접 접근 시 `404`를 반환하고 데이터를 변경하지 않음
- 공지 관리: `/api/v1/branches/:branchId/notices`, `/api/v1/me/notices/:noticeId/read`, `/api/v1/me/notices/bulk-read`
  - 지점 전체, 반 대상, 개인 대상 공지와 역할 audience, 중요 공지, 읽음 상태, 미읽음/중요 필터, 보이는 공지 읽음 처리, 확인할 공지를 지원
  - 대표/총괄은 역할 대상 audience를 수정할 수 있지만 코치는 기존 audience를 유지해야 합니다. 반·개인 대상은 생성 후 수정하지 않습니다. 제목·본문·중요 여부·audience가 실제로 바뀌면 기존 읽음 상태를 초기화하고, 동일 내용 재저장은 읽음 상태를 보존합니다. 수정과 읽음 쓰기는 직렬화하며, 수정 감사 로그는 본문 원문 대신 본문 길이와 변경 여부만 기록하고 공지 수정만으로 휴대폰 푸시를 다시 발송하지 않습니다.
- 공지 작성/일괄 읽음, 알림 구독/해지는 세션과 역할/대상 접근 권한을 요청 본문 검증보다 먼저 수행합니다. 삭제된 요청 API는 제공하지 않아 본문을 처리하지 않습니다.

서버는 httpOnly 쿠키 세션을 사용하고, 응답 스냅샷은 역할/지점/자녀 관계 기준으로 마스킹됩니다. `.data/`는 런타임 데이터라 git에 포함하지 않습니다.
JSON 저장소는 원자적 파일 교체, 최신 스냅샷 백업, 깨진 primary JSON 복구, 기본 collection shape 검증과 파일시스템 기반 요청·읽기·쓰기 잠금을 수행합니다. 서로 다른 프로세스와 저장소 인스턴스도 조회와 쓰기 직전에 디스크 최신본을 다시 읽어 오래된 메모리 캐시를 갱신하고, 같은 base에서 시작한 서로 다른 변경은 컬렉션 ID와 필드 단위 3-way merge로 보존합니다. 사용자 휴대폰·이메일 유일성과 핵심 참조는 병합 후 다시 검증하되 읽기 중 자동 정정하지 않습니다. 기존 고아 참조는 구조화된 진단으로 확인하고, 쓰기 전후 비교로 새 결함만 차단합니다. 명시적 복구는 실제 변경마다 `system.integrity.repair` 감사 기록을 남기며 출석·결제 이력을 자동 삭제하지 않습니다. 백업은 `.data/backups/`에 최대 20개 유지되며 2분 이상 남은 비정상 lock만 stale lock으로 정리합니다.
PostgreSQL 런타임 저장소는 `app_runtime_state` JSONB 테이블에 같은 운영 스냅샷과 revision을 저장하며, 기존 route handler/API 계약을 바꾸지 않고 운영 DB를 사용할 수 있게 합니다. 결제 등록 재시도는 같은 DB 트랜잭션 연결의 PostgreSQL advisory lock으로 여러 서버 인스턴스 사이에서도 같은 요청 키를 직렬화하고, 서로 다른 도메인의 stale snapshot 쓰기는 row lock 뒤 최신 revision에 3-way merge합니다.

운영 데이터 호환성 확인은 운영 DB 자체가 아닌 승인된 복제 JSON 스냅샷으로 `npm run preflight:runtime-snapshot -- --file=<snapshot>`을 실행합니다. 출력은 규칙별 집계만 포함합니다. `npm run runtime:integrity:reconcile -- --file=<snapshot> --actor-user-id=<admin-user-id>`은 기본 dry-run이며, 감사 actor는 스냅샷 안의 승인 완료 총괄 어드민이어야 합니다. `--write`는 백업·롤백 계획과 별도 승인을 확보한 격리 데이터에만 사용합니다.

`test:release`는 위 품질/보안 audit/저장소/preflight/스모크/DB/파일럿 데이터/접근성 게이트를 순서대로 실행하는 파일럿 전 통합 검증입니다. smoke/E2E 구간에서는 빈 로컬 포트와 임시 JSON 저장소를 만들고 직전에 지문을 확인한 production build를 `next start`로 실행한 뒤 서버와 데이터를 정리합니다. 데모 로그인·reset 허용 플래그는 이 격리 자식 프로세스에만 적용됩니다. `SMOKE_BASE_URL`을 직접 지정하려면 서버가 없는 로컬 HTTP origin이어야 하며, 이미 응답하는 서버나 원격 origin은 현재 작업 트리 검증으로 재사용하지 않습니다. 실행 중인 개발 서버는 종료하거나 재사용하지 않습니다. Docker Desktop은 DB smoke를 위해 별도로 실행 중이어야 합니다.
Next 16.2.9의 내부 PostCSS 보안 advisory는 `package.json`의 `overrides`로 `postcss@8.5.10`을 고정해 `npm audit --audit-level=moderate` 0건을 확인합니다.

모바일 앱 배포 상태는 Android 산출물, iOS Simulator, App Store Connect 배포를 별도로 표시해 `Simulator 성공과 IPA 배포 가능 상태`를 혼동하지 않습니다. iOS Local Profile Inventory는 Team ID, bundle id, export method별 `matching provisioning profile`과 등록 기기 포함 profile 수를 함께 기록하되 Development/Ad Hoc에서만 기기 등록을 필수로 보고 UDID 원문은 저장하지 않습니다. `보류 중인 외부 준비`는 실제 미해결 origin/profile만 표시하며, 나머지 외부 증빙이 사용자 보류이면 전체 출시 판단은 보류 상태를 유지합니다.

## PostgreSQL 런타임 저장소

개발/파일럿/운영 환경 변수 전체 기준은 `docs/ENVIRONMENT_MATRIX.md`와 `.env.example`, `.env.production.example`에 정리되어 있습니다. 파일럿에서 파일 저장소 대신 PostgreSQL을 쓰려면 다음 환경 변수를 설정합니다.

```bash
FINAL_JUDO_DB_DRIVER=postgres
FINAL_JUDO_POSTGRES_URL=postgresql://user:password@host:5432/final_judo
```

선택 값:

```bash
FINAL_JUDO_POSTGRES_STATE_KEY=mvp
FINAL_JUDO_POSTGRES_TABLE=app_runtime_state
```

정규화 PostgreSQL 스키마와 seed는 `db/migrations/`와 `db/seeds/`에 있고, 현재 Next.js route handler는 전환 안정성을 위해 `app_runtime_state` JSONB 스냅샷을 사용합니다.

## 파일럿 데이터 반영

파일럿 직전에는 먼저 dry-run으로 변환 결과를 확인합니다.

```bash
npm run test:pilot
npm run test:pilot-import
```

검증 후 실제 런타임 JSON DB에 반영할 때만 `--write`가 포함된 명령을 실행합니다. 이 명령은 `.data/final-judo-db.json`을 갱신하고 JSON 저장소 백업을 남깁니다.

```bash
npm run pilot:import -- docs/pilot-templates/pilot-data-intake.csv
```

PostgreSQL runtime store에 반영할 때는 Postgres 연결 환경 변수를 먼저 설정한 뒤 다음 명령을 사용합니다.

```bash
FINAL_JUDO_DB_DRIVER=postgres
FINAL_JUDO_POSTGRES_URL=postgresql://user:password@host:5432/final_judo
npm run pilot:import:postgres -- docs/pilot-templates/pilot-data-intake.csv
```

실제 파일럿 데이터를 반영한 뒤에는 개발/테스트 전용 `/api/v1/dev/reset`을 호출하는 smoke 명령을 실행하면 데모 기준 데이터로 되돌아갈 수 있으니, 운영 확인 중에는 사용하지 않습니다.

파일럿 전 현장 확인은 총괄 어드민으로 `/app/admin/settings`에 접속해 항목별 상태, 담당자, 증빙을 저장합니다. 여기에는 기본 임시 비밀번호의 계정별 교체와 전달 채널 확인도 포함됩니다. 파일럿 중 P0/P1/P2 이슈가 생기면 같은 화면의 파일럿 이슈 로그에 심각도, 재현 절차, 우회책, 상태를 기록합니다. 파일럿 2주 운영 중에는 일일 운영 로그에 운영 일자, 지점, 수업/출석/결제/요청/공지 확인 수치, 모바일 출석 처리 시간과 현장 녹화/캡처 증빙, 증빙 메모를 남깁니다. `verified` 또는 `blocked` 상태와 이슈의 `monitoring`/`resolved` 상태는 증빙 또는 조치 메모가 필요하며, 모든 변경은 변경 기록에 남습니다.
준비 초안 전체는 `npm run pilot:prelaunch-draft -- --out-dir=.data`로 먼저 생성할 수 있습니다. 이 명령은 현장 준비 증빙 CSV, 계정별 비밀번호 교체 CSV, audit launch package, pre-pilot evidence/preflight/status, 요약 JSON을 한 번에 남기고 blocked next action을 표시합니다.
현장 준비 증빙은 `npm run pilot:readiness-evidence:draft -- --phase=pre-pilot --out=.data/pilot-readiness-evidence.csv`로 먼저 CSV 초안을 만든 뒤 owner/status/evidence를 채워 `npm run pilot:readiness-evidence -- --file=.data/pilot-readiness-evidence.csv --phase=pre-pilot`로 검증합니다. 검증된 CSV는 `npm run pilot:readiness-evidence:apply -- --file=.data/pilot-readiness-evidence.csv --phase=pre-pilot --actor-user-id=user-admin`로 런타임에 반영하거나 `/app/admin/settings`에서 직접 입력합니다. 이 CSV는 `/app/admin/settings` 입력 전 사전 점검용이며, 최종 기준은 앱에 저장된 준비 항목과 변경 기록입니다.
계정별 비밀번호 교체 증빙은 `npm run pilot:password-rotation:draft -- --runtime=.data/final-judo-db.json --out=.data/pilot-password-rotation.csv`로 CSV 초안을 만든 뒤, `/app/admin/users`의 임시 비밀번호 발급 변경 기록와 전달 채널 증빙을 확인해 `npm run pilot:password-rotation -- --runtime=.data/final-judo-db.json --file=.data/pilot-password-rotation.csv`를 통과시킵니다. 이 CSV에는 원문 임시 비밀번호를 적지 않고, 변경 기록 ID와 전달 채널 증빙 링크만 남깁니다.

운영 배포에서 `/api/v1/dev/reset`은 기본 비활성화됩니다. production 환경에서는 `FINAL_JUDO_ENABLE_DEV_RESET=1`만으로 열리지 않으며 강한 실행별 소유권 토큰과 해당 실행이 만든 임시 JSON 저장소 마커까지 필요합니다. PostgreSQL과 공유 `.data`는 이 API로 초기화할 수 없습니다.
운영 배포에서 데모 역할 로그인도 기본 비활성화됩니다. 실제 파일럿에서 임시 역할 선택 로그인이 필요하면 `FINAL_JUDO_ENABLE_DEMO_LOGIN=1`을 설정하고, 파일럿 종료 후 제거합니다.
운영 배포 전 `npm run test:env-readiness`로 환경 변수 매트릭스, `.env.production.example`의 위험 플래그 기본값, PostgreSQL/결제/푸시 placeholder, 릴리즈 게이트 문서 정합성을 확인합니다.
운영 secret을 배포 플랫폼에 입력하고 production preflight/release가 통과한 뒤에는 `npm run deployment:handoff:draft -- --out=.data/deployment-handoff.json --preflight-report=.data/pilot-preflight.pre-pilot.json`로 secret 원문 없이 초안을 만들고, 증빙 필드를 채운 다음 `npm run deployment:handoff -- --file=.data/deployment-handoff.json --out=.data/deployment-handoff.report.json`로 검증합니다. manifest에는 실제 secret 값을 넣지 않고 secret 이름, 보관 위치, 증빙만 기록합니다.
운영 배포 전 기본 임시 비밀번호 `FinalJudoPilot!2026`은 계정별 값으로 교체하고, 운영 중 API 응답에 `passwordHash`가 포함되지 않는지 `npm run test:smoke`로 재확인합니다.
실제 파일럿 데이터를 반영하고 `/app/admin/settings` 증빙을 채운 뒤에는 `NODE_ENV=production npm run preflight:pilot -- --out=.data/pilot-preflight.pre-pilot.json`을 실행해 배포 전 차단 조건이 없는지 최종 확인하고 결과 JSON을 보관합니다.
파일럿 시작 전 전체 산출물을 한 번에 만들려면 `npm run pilot:launch-package -- --csv=docs/pilot-templates/pilot-data-intake.csv --readiness-evidence=.data/pilot-readiness-evidence.csv --password-rotation=.data/pilot-password-rotation.csv --out=.data/pilot-launch-package.json`을 실행합니다. 이 명령은 `.data/pilot-evidence.json`, `.data/pilot-evidence.pre-pilot.md`, `.data/pilot-preflight.pre-pilot.json`, `.data/pilot-launch-package.json`을 생성하고 strict preflight나 준비/비밀번호 교체 증빙이 차단되면 패키지를 남긴 뒤 실패합니다. PostgreSQL 운영 DB에서는 `--driver=postgres --state-key=<key> --postgres-url=<url>`을 함께 사용하고, 보관되는 패키지의 명령 provenance에는 DB URL 비밀번호가 `REDACTED`로 남습니다. 준비 중 리허설은 `--allow-incomplete`를 붙입니다.
파일럿 2주 운영과 종료 회고까지 마친 뒤에는 `NODE_ENV=production npm run preflight:pilot -- --require-retro --out=.data/pilot-preflight.post-pilot.json`를 실행해 실제 운영 증빙까지 최종 확인합니다.

--post-pilot-evidence=.data/pilot-evidence.post-pilot.json --post-pilot-markdown=.data/pilot-evidence.md --out=.data/pilot-field-evidence.json`로 source CSV/운영 수치가 채워진 manifest 초안을 생성합니다. 이후 실제 현장 값과 회원 앱의 현재 기준은 `회원 홈`/`오늘 요약` 같은 보조 제목 없이 다음 수업, 출석, 결제 상태, 상담/공지 상태를 한 패널 안에서 압축해 보여주고, 학부모 앱은 `학부모 홈` 소개문 없이 자녀별 학습 리포트에서 단계/피드백/심사/대회 정보를 우선 보여주는 것입니다. 총괄/코치 공통 대시보드는 `역할명 홈` 대신 `대시보드` 제목으로 바로 지표를 보여줍니다. 코치 대시보드는 결제 운영 카드 대신 오늘 수업 명단의 상담/주의 회원을 보여주고, 코치 모바일 출석은 상태 필터를 가로 칩 레일로 유지하며 중복 요약 카드를 줄여 첫 화면에서 명단 조작을 먼저 보이게 합니다. 다음 행동 큐, 오늘 확인 브리프, 주간 확인 리듬, 복귀 안내 레일, 수업 전 준비 보드, 확인 리마인드 큐 같은 내부 운영 안내는 회원/학부모 화면에 노출하지 않습니다. 회원/학부모 `/app/payments`는 금액 중심 요약 카드나 CSV/운영 보드 없이 회원권 상태, 납부일, 만료일 중심의 간단한 리스트로 보여줍니다. 대표 운영 리포트도 반복 설명문 대신 제목, 지표, 다음 확인을 먼저 보여줍니다. `/app/requests`와 `/requests`는 제공하지 않고 요청 생성/승인/반려 API도 `404` 삭제 상태를 유지합니다.
